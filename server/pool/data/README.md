# Pool data files

Files the Node service reads at start for the views of game records
([docs/analytics-records.md](../../../docs/analytics-records.md)). They are part of `server/pool`, so a pool deploy
(`git archive server/pool`) carries them; a change is a commit and an ordinary pool deploy, which the owner has
allowed in advance for this program (TASK-2026-11-26-pro-collection, "Деплой пула"). Nothing here comes from players.

| File | Kept by | Read by | Updated when |
|---|---|---|---|
| `balance-patches.json` | by hand, by whoever ships the pool after a Hearthstone patch | `node/records/periods.mjs` | a patch changes cards (Constructed, Battlegrounds or Arena) |
| `archetypes.json`, `card-ids.json` | generated by `tools/archetypes/server_dictionary.py` (package B1), committed as generated | `node/records/derive/archetypes.mjs` | at a patch, after the archetype list changes; the command is in the script's docstring |

## balance-patches.json

```json
{ "v": 1, "lines": { "constructed": [ { "id": "b256589", "fromBuild": 256589, "fromDay": 20760 } ],
                     "battlegrounds": [ … ], "arena": [ … ] } }
```

- One list per line: `constructed` counts Ranked, `battlegrounds` solo and duos, `arena` Arena games and run summaries.
- An entry starts a balance patch: `fromBuild` is the first client build of the patch (`GameState.BuildNumber`, the
  `build` of a record), `fromDay` the day it came out (days since 1970-01-01, UTC), `id` the patch version (`34.6.2`)
  or `b<fromBuild>` when the version is not known. A build belongs to the entry with the highest `fromBuild` not above
  it; a build below the first entry, or a record without a build, is "unknown".
- Builds without card changes (client hotfixes) stay in the patch: add an entry only when cards changed for that line.
  A Battlegrounds balance update without a new client build cannot be told apart by build: it waits for the next build,
  or is entered at that build later.
- The views show the newest patch (whole, last 7 days, last 30 days) and the previous one (whole). A forgotten entry
  merges two patches; an entry at the wrong build splits one. Both only move numbers between windows; nothing is lost.
- How to add one: append the entry to each line whose cards changed, keep every list in build order (the service
  refuses a later build with an earlier day, a repeated id or build, or an unknown line, and then runs with every view
  switched off: `records_patches_invalid` in the journal), run `node --test server/pool/test/records-periods.test.mjs`,
  commit, deploy the pool. The views rebuild within a minute of the restart (the file is part of their signature).
- Find the build: HearthstoneJSON lists the builds (`https://api.hearthstonejson.com/v1/`; the newest folder is the
  newest build, the `Last-Modified` of its `enUS/cards.json` is near its release), or a fresh `Power.log`.
- The first entry (2026-11-26) is build 256589, HearthstoneJSON's newest on that day, released 2026-11-03 (day 20760),
  for all three lines. Records sent before the app writes `build` stay "unknown" for good.
