# План доведения Hearthpulse до функционального аналога HSReplay / HDT / Tier7

Дата: 2026-11-15. База кода: `main` @ `f2dbdca6` (все ссылки на строки) и сверка с `ed25702b` (установка семи
скиллов; код приложения между ними не менялся). Исходный отчёт:
[research/2026-11-15-hsreplay-parity-and-skills.md](../research/2026-11-15-hsreplay-parity-and-skills.md).
Это план, код не менялся. На production ничего не отправлялось: только GET без авторизации.

Разрешение на данные HSReplay и HSGuru закрыто решением владельца
([data-permissions.md](../data-permissions.md)) и здесь не обсуждается.

## 0. Главное за минуту

1. **Половина «разрывов» закрывается данными, которые у нас уже есть.** API данных уже отдаёт муллиган по
   конкретной колоде (`/v1/hsreplay/mulligan?deck=…`, 12 колод Standard и 6 Wild на каждый из 4 рангов), свежесть
   каждого из 110 источников (`/v1/system/sources`), композиции BG с трайбами и ключевыми картами и тринкеты по
   срезам MMR. Приложение их либо не читает, либо читает только во вкладках, а советник в игре ждёт те же данные
   из пустого пула (`BattlegroundsAdvisor.cs:84-90`). Это правка клиента, а не новый сервер и не новые данные.
2. **Свой контур не «не построен», а остановлен на трёх выключателях.** Сервис пула работает на сервере 151 с
   2026-11-09, но (а) выкладка старше пакета аналитики: nginx не знает `/stats/v2/…` и отвечает 404; (б)
   `PoolClient.DefaultEndpoint = ""`, поэтому ни одна установка ничего не шлёт; (в) условие включения из
   `source-capture-verification.md` не выполнено: политика приватности сайта называет хостингом пула Cloudflare
   (США), а сервис стоит на сервере 151, и про исходные захваты там нет ни слова.
3. **В пуле три независимых хранилища, и это надо учитывать в каждом пункте.** Таблица `g` (`/v1/games`, только
   по согласию, только из WPF) кормит `/v1/stats`, который читает советник BG. Таблица `e` (`/v1/events`, по
   умолчанию включено, оба UI) кормит только `/v1/events/summary`. Захваты (`/v1/captures`, оба UI) кормят
   `/v2/analytics`. Поэтому «включить пул» само по себе не наполнит `heroTribes` для совета под лобби.
4. **Слова владельца требуют только:** выкладка на сервер 151, публикация текста политики на сайте, релиз и тег,
   покупка сертификата и секреты подписи, регистрация расширения Twitch, рост расходов на сбор данных и четыре
   выбора поведения (раздел 7). Всё остальное идёт обычным `hearthpulse-ship`.

Слои данных названы как в скилле `hearthpulse-analytics`: внешние данные; общие игры (`g`); записи игр (`e`);
захват → факты → снимок. Готовность называется одним из трёх слов: **статически** (код и тесты), **развёрнуто**
(маршрут отвечает на хосте), **производит** (числа проходят пороги).

## 2. Проблемы: причина, готовое, изменения, приёмка

Объём: **S** дни, **M** одна-две недели, **L** больше. Оценка относительная и без учёта ожидания владельца,
ревью Twitch и накопления выборки. В каждом пункте помечено: **исправление** существующего или **новая**
возможность.

### 2.1. Свой контур: игра → отправка → агрегат → экран (исправление)

**Доказательства (2026-11-15).**

| Запрос | Ответ | Вывод |
|---|---|---|
| `GET …/stats/v1/stats?mode=solo` | 200, `games: 0`, все списки пусты | таблица `g` пуста |
| `GET …/stats/v1/events/summary` | 200, `games: 0` | таблица `e` пуста |
| `GET …/stats/v1/choices` | 200, `games: 0` | общих игр Constructed нет |
| `GET …/stats/v1/meta` | 503 `meta not imported` | базовой меты нет, это ожидаемо (`server/pool/README.md`) |
| `GET …/stats/v2/analytics/bg/heroes?mode=solo` | **404 от nginx** | в выложенном сниппете нет `location = /stats/v2/analytics/bg/heroes`; в репозитории он есть (`server/pool/deploy/nginx-source-capture.conf`) |
| `GET …/stats/healthz` | 403 | как задумано: только loopback |
| `GET …/stats/v1/captures/status` | 405 `method_not_allowed` от сервиса | сервис жив и проксируется |

**Причины.**

1. Выкладка 2026-11-09 сделана до пакета аналитики (`9ed3ccb1`: приём источника v2, миграция `0009`, маршрут
   v2). `docs/source-capture-verification.md` фиксирует на хосте декодер `source-v1.2`; текущий код пишет
   источник v2 и ждёт `source-v2.0`. `docs/analytics-api.md`, «Rollout order»: сначала сервер, потом воркер v2,
   потом клиенты и адрес по умолчанию.
2. `src/Hearthpulse.Core/Pool/PoolClient.cs:19` `DefaultEndpoint = ""`; `Available` требует `https://`
   (`:57`). От него зависят все три отправителя: `GameStatsClient.Sharing` (`GameStats/GameStatsClient.cs:36`),
   `SourceCaptureClient.Sharing` (`SourceCapture/SourceCaptureClient.cs:13-14`), `PoolClient.Sharing` (`:60`), и
   чтение `PoolClient.OverlayAsync` (`Battlegrounds/BattlegroundsMeta.cs:290-305`). Поля для адреса в интерфейсе
   нет, только `settings.json` (`AppSettings.cs:223`).
3. Условие включения не выполнено: `HeartPulse/src/modules/legalPages/content.json` (версия от 2026-11-06,
   PR #352) говорит «Данные уходят… на отдельный сервер статистики Hearthpulse у Cloudflare, Inc. (США)» и
   описывает только общие игры BG (60 дней) и записи игр (180 дней). Исходных захватов, драфтов Арены и сервера
   151 в тексте нет. Не подтверждено и удаление из резервных копий хоста (на 151 идут `server-backup-*` restic →
   OVH S3, `server-151.md:158`).
4. `AnalyticsClient.LoadBgHeroesAsync` (`Pool/AnalyticsClient.cs:36`) не вызывает ни один экран
   (`docs/analytics-api.md`: «No screen uses it yet (B1)»).
5. Пилотные лимиты малы: 256 МБ архива, 128 МБ и 1000 захватов в сутки (`deploy/pool.env.example`).

**Готово и переиспользуется.** Сервис, systemd-юнит, nginx-сниппеты, `synthetic-smoke.mjs`, runbook; миграция
`0009` применяется сама при старте; `Hearthpulse.SourceWorker` v2; очереди и повторы `GameStatsUploader` и
`SourceCaptureQueue`; уведомление и выключатель в обоих UI (`Presentation/Main/MainViewModel.GameStats.cs`);
клиент аналитики с тестами (`AnalyticsClientTests`); вкладка героев BG с датой данных
(`MainViewModel.BgSite.cs:394`).

**Изменения.**

- **Сервер 151 (выкладка, слово владельца).** Обновить `/opt/hearthpulse-pool/app` до текущего `main`; собрать и
  положить `Hearthpulse.SourceWorker` (команды в `LINUX-RUNBOOK.md`, «Real .NET worker»); заменить nginx-сниппет
  на версию из репозитория и добавить зону чтения `hearthpulse_stats_read`
  (`nginx-source-capture-limits.conf`); `nginx -t`, reload; smoke по loopback и по HTTPS. Данные сервиса не
  трогать, журнал отзывов `private/revocations.jsonl` не откатывать.
- **Сервер, код (`server/pool`, обычный workflow).** В `/healthz` уже есть счётчики захватов; добавить возраст
  последнего снимка аналитики и число записей `e` и `g` за сутки, чтобы «жив» отличалось от «производит»
  (правило `hearthpulse-observability`: поле в `/healthz` раньше новой строки лога).
- **Core.** Новый небольшой загрузчик `Pool/OwnBgHeroes.cs` рядом с `AnalyticsClient`: кэш `cache/api`
  (30 минут, атомарная запись, старая копия офлайн), состояния `not_configured | offline | not_published |
  rebuilding | small_sample | ok`. `DefaultEndpoint` меняется последним коммитом этапа.
- **Presentation.** `Main/MainViewModel.BgOwn.cs`: блок «Статистика Hearthpulse (свои игры)» на вкладке героев
  BG: герой, предложен, взят, доля выбора с интервалом, среднее место с интервалом, число установок и захватов,
  дата публикации. Пустые состояния раздельные (правило «absence is a value»). Своё число, которого нет, не
  подменяется внешним; внешние числа вкладки остаются как есть и со своей датой.
- **WPF и Avalonia.** Один и тот же блок в `App/Main/Pages/BattlegroundsPage.xaml` и
  `UI/Main/Pages/BattlegroundsPage.axaml` из существующих стилей таблиц; строки в обоих языках.
- **Сайт (репозиторий HeartPulse, слово владельца на публикацию).** Раздел 9 политики: хостинг пула — сервер
  Hearthpulse (указать фактическую страну и оператора вместо Cloudflare), новая категория «упорядоченный журнал
  видимых событий игры и драфта», срок 180 дней, удаление по выключателю, оговорка про резервные копии хоста
  ровно такая, какую подтвердит проверка.
- **Проверка резервных копий (сервер, чтение).** Убедиться, что `/var/lib/hearthpulse-pool` не входит в наборы
  `server-backup-*`, либо записать срок жизни копий. Без этого обещать удаление из копий нельзя
  (`hearthpulse-privacy`, правило 6).

**Порядок.** Выкладка сервера → воркер v2 → пилот через `PoolEndpoint` в `settings.json` (владелец и
тестеры) → политика и проверка копий → `DefaultEndpoint` → релиз.

**Данные и пороги.** Строка героя публикуется от 5 установок, значение от 10 игр в знаменателе
(`docs/analytics-api.md`); группировка по `build`, сборки не сливаются. Для первой опубликованной строки нужно,
чтобы одного героя предложили пяти разным установкам в пределах одной сборки игры за 30 дней. При 5–10
установках пилота это первые строки через несколько дней игры; полный список героев требует сотен игр на сборку.
Пилотный потолок 1000 захватов в сутки покрывает десятки активных установок; перед релизом поднять
`POOL_ARCHIVE_BYTES` и `POOL_DAILY_*` по замеру пилота (в runbook свободно 44 ГиБ на дату отчёта P4).

**Приёмка.**

- `GET …/stats/v2/analytics/bg/heroes?mode=solo` отвечает JSON `available: false, reason: "not_published"`, а не
  404; `mode=duos` → `unsupported_mode`; POST на тот же адрес отклонён.
- После одной игры владельца с `PoolEndpoint`: в `hearthpulse.log` строка `Game stats: sent 1 game(s)`;
  `/stats/v1/events/summary` показывает `games ≥ 1` после пересборки; захват в `/healthz` в статусе `parsed` или
  `partial`, не `failed`.
- В обоих UI блок своих данных показывает одно и то же состояние и одну и ту же дату для одного ответа; при
  выключенном пуле блока нет; при `not_published` — текст «данных пока нет», без чисел.
- Выключение отправки: очереди пусты, `/v1/events/forget` и `/v1/captures/forget` приняты; ответ 202 показан как
  «удаляется», не как «удалено».

**Проверки.** Локально: `node --test server/pool/test/*.test.mjs`; локальный сервис с
`ANALYTICS_MIN_SOURCES` только для стенда (в production не задавать) и пять синтетических установок →
блок показывает числа; `dotnet test` обоих наборов; рендер обоих UI (`hearthpulse-visual-check`). Интеграция:
`synthetic-smoke.mjs` против loopback и HTTPS. Вживую: таблица GET выше до и после.

**Риски и откат.** Сниппет nginx откатывается из резервной копии предыдущего файла; сервис — предыдущим
каталогом `app`; миграция `0009` аддитивная. Клиент со старым декодером на сервере получил бы `failed` у всех
захватов v2: поэтому воркер ставится до пилота. Откат клиента — пустой `DefaultEndpoint` следующим релизом.

**Объём.** Сервер S (при готовом доступе), клиент и оба UI S–M, политика S, накопление выборки — календарное.

### 2.2. Отправка в пул только в WPF (исправление)

**Причина.** `ShareWithPool` и `ShareHistoryAsync` живут в хосте WPF (`src/Hearthpulse.App/App.StatsPool.cs:19,61`,
вызовы `App.xaml.cs:199,388,464`). Свойства согласия `PoolAvailable`, `AskPoolConsent`, `PoolSharing`,
`PoolConsentChanged` — в WPF-части модели (`App/Main/MainViewModel.cs:15-50`); общая часть прячет команду
`AnswerPool` и условие уведомления под `#if HEARTHPULSE_WPF` (`Presentation/Main/MainViewModel.cs:58-64`,
`MainViewModel.GameStats.cs:75-77`). Баннер есть только в `App/Main/MainWindow.xaml:476-499`, выключатель только
в `App/Main/SettingsTabs/DataSettings.xaml:25`. В `UI/AppHost.cs:542-551` `OnGameFinished` в пул ничего не шлёт.
Записи игр и захваты уже общие (`Core/Hosting/AppServices.cs:70-73`), поэтому Avalonia наполняет `e` и захваты,
но не `g`.

**Готово.** Вся логика в Core (`PoolClient`, `PoolGame`, `ConstructedPoolGame`), строки локализации
(`Main.Pool.*`, `Settings.Data.PoolSharing*`), образец общего хоста `Core/Hosting/SourceCaptureHost.cs`.

**Изменения.**

- **Core.** `Hosting/PoolSharingHost.cs`: принимает `AppSettings`, `HttpClient`, `HistoryStore`,
  `Func<CardDb>`; методы `OnGameFinished(GameOutcome)`, `ShareHistoryAsync()`, событие `SettingsChanged` (хост
  сохраняет настройки после создания секрета и флага `PoolHistoryShared`). Создаётся в `AppServices`,
  подписывается на `Session.GameFinished`. Поведение один в один с `App.StatsPool.cs`, включая «только первый
  вызов до рейтинга» и `PoolClient.Limit`.
- **Presentation.** Перенести четыре свойства согласия в общий `Main/MainViewModel.Pool.cs`, убрать оба `#if`.
- **WPF.** Удалить `App.StatsPool.cs`, заменить три вызова на хост; разметку не менять.
- **Avalonia.** Баннер согласия в `UI/Main/MainView.axaml` (рядом с уведомлением о записях, строка ~558) и
  выключатель в `UI/Main/SettingsTabs/DataSettings.axaml`; в `AppHost` — `PoolAvailable` и подписка на
  `PoolConsentChanged`.

**Приёмка.** Тест хоста с поддельным обработчиком: при согласии версии 4 игра BG даёт один `POST /v1/games`,
игра Constructed с выборами — один `POST /v1/constructed`; без согласия и при версии ниже нужной — ничего или
урезанное тело. `tests/Hearthpulse.Presentation.Tests`: уведомление о записях в обоих UI ждёт ответа на вопрос
пула. Рендеры баннера и выключателя в обоих UI, ru и en.

**Ограничение, которое остаётся.** У `/v1/games` нет очереди и повтора: игра, законченная офлайн, теряется; у
маршрута нет и удаления по запросу, только срок 60 дней (`hearthpulse-privacy`, правило 6). Это не чинится
переносом; чинится решением D1 из раздела 7.

**Объём.** S. Зависимостей нет, можно делать параллельно с 2.1.

### 2.3. Коллекция, «могу собрать», пыль (новая)

**Причина.** Модуля нет: в `Core/Memory` читаются рейтинг, трайбы лобби, цены кнопок, игроки, драфт Арены
(`HearthstoneMemory.*.cs`), коллекции нет. В логах коллекции нет вовсе.

**Готово.** Чтение Mono-объектов (`MonoRuntime`, `MonoObject`, `HearthstoneMemory.FindNetCacheObject`,
`HearthstoneMemory.cs:328`), поток `MemoryPoller`, тестовый образ памяти (`MonoImageBuilder`, `MemoryImageTests`),
инструмент `tools/Hearthpulse.Probe class <Имя>`, редкость и набор карты в `CardDb`, коды колод `DeckString`,
списки колод меты и страница своей колоды.

**Изменения.**

- **Разведка (шаг 0, нужен запущенный клиент).** `Probe class` по объектам сетевого кэша коллекции и баланса
  пыли; записать найденные имена и смещения в `docs/collection.md` с заявлением «имена взяты из клиента, код HDT
  не читался» (правило лицензий: у HDT только идеи).
- **Core.** Новый модуль `Core/Collection/` с узким интерфейсом: `Collection` (число обычных и золотых копий по
  id карты, пыль, время чтения), `CollectionStore` (файл `collection.json` в папке данных, атомарно),
  `DeckCost.For(deck, collection, cards)` → каких карт не хватает, сколько пыли нужно, можно ли создать
  (обычная 40/100/400/1600 по редкости; несоздаваемые наборы помечаются отдельно, а не оцениваются в 0).
  `Memory/HearthstoneMemory.Collection.cs` — только чтение; опрос при входе в меню коллекции и раз за запуск.
- **Presentation и оба UI.** В списках колод меты и на странице архетипа — метка «есть» / «не хватает N пыли» и
  фильтр «могу собрать»; на странице своей колоды — недостающие карты. На macOS и Linux и до первого чтения —
  честное пустое состояние «коллекция читается из клиента на Windows».
- **Правовая проверка.** Перед слиянием — отчёт агента `hearthpulse-legal` (правило CLAUDE.md для чтения
  памяти). Это шаг процесса, а не вопрос владельцу: чтение без записи уже принято в ADR 0006.

**Вне объёма первой версии.** Загрузка коллекции на сайт и публичная ссылка (новый поток данных: отдельное
уведомление и контракт сайта), рекомендации «что создать».

**Приёмка.** Тесты на поддельном обработчике: точное совпадение → числа колоды; два отличия → «близкая»; нет

#### 2.4.3. BG в игре: композиции, тринкеты, поправка на лобби (исправление + новая)

**Причина.** `BattlegroundsAdvisor.cs:84-90,128`: композиции и тринкеты берутся из `meta.Comps` и

**Изменения.**

- **Core.** `BattlegroundsMeta.WithExternal(BgSiteStats)`: строит `MetaComp` и `MetaTrinket` из уже загруженных

  порога — она главнее.

  хранимого набора `hsreplay_battlegrounds_hero_details`, чтобы не делать 116 запросов по 150 КБ.

  это минимальная выборка, совместимая с округлённым распределением), число игр как точное не показывать.

**Ограничения.** Поправка на лобби есть только для топ-50 %; на macOS и Linux трайбы лобби не читаются
(память). Гайды по героям, аномалиям и квестам — контент, см. 2.10.

**Приёмка.** `AdvisorTests`: при пустом пуле и загруженных внешних списках на выборе героя появляются две

### 2.8. Реплей по ссылке, загрузка в профиль, Twitch

**Реплеи и профиль (исправление: осталась только живая проверка).** Статически готово: `Replay/ReplayUpload.cs`,
`Accounts/AccountClient.cs` (`POST tracker/replays`), `Accounts/ProfileUploader.cs`. Развёрнуто, судя по ответам:

### 2.9. Подпись обновлений и установщиков, выпуск версии

**Причина.** Вся механика есть: проверка Ed25519 в клиенте (`Updates/UpdateSignature.cs`, `Ed25519.cs`),
`installer/sign-sums.sh`, `installer/windows/sign.sh`, шаги в `.github/workflows/release.yml:131-135,227-245`,
пробный режим `sign_selftest`. Нет самих ключей: `Updates/update-signing-key.pub` содержит только комментарии
(«transition mode»), `gh secret list` для репозитория пуст, сертификата Authenticode нет, macOS не нотаризуется.
Версия в проектах 0.15.0, опубликована 0.14.0.

**Порядок (ловушка из скилла `hearthpulse-release`: ключ в сборке без секрета валит публикующий запуск, а
клиенты с ключом перестают принимать неподписанное).**

1. Владелец создаёт ключ (`openssl genpkey -algorithm ed25519`), закрытую часть кладёт в секрет
   `UPDATE_SIGNING_KEY` и хранит копию вне GitHub.
2. Обычным workflow: открытый ключ в `update-signing-key.pub`, ссылка в `Hearthpulse.Core.csproj`, пробный
   запуск `release.yml` с `publish: false` — подпись создана и проверена встроенным ключом.
3. До появления секретов подписи — разовый аудит workflow по скиллу `hearthpulse-ci-security` (в отчёте: 40
   строк `uses:` без привязки к SHA).
4. Релиз 0.15.0 по чек-листу `reference/tasks/TASK-2026-11-09-update-delivery/release-checklist.md` — по слову
   владельца. С этого релиза каждый следующий обязан быть подписан; второй ключ для ротации добавить заранее.
5. Authenticode: Azure Trusted Signing или сертификат OV/EV — расходы и проверка личности, решение владельца;
   секреты `WINDOWS_SIGN_PFX*` или `AZURE_SIGNING_*` уже поддержаны. До этого — предупреждение SmartScreen.
6. Нотаризация macOS — Apple Developer, P2.

**Приёмка.** Клиент 0.15.0 принимает обновление с верной подписью и отклоняет изменённый байт и чужой ключ
(`UpdateSignatureTests`, плюс живой прогон обновления 0.15.0 → следующая версия); установщик Windows показывает
издателя. **Откат.** Потеря закрытого ключа без второго встроенного останавливает автообновление для всех
установок с ключом: поэтому два ключа и копия вне GitHub — до первого подписанного релиза. **Объём.** S (ключ
обновлений), S–M (Authenticode после покупки).

## 8. Риски плана

- **Малая база установок.** Свои метрики с порогами 5 установок и 200 игр на пару могут оставаться пустыми
  месяцами. План поэтому сначала закрывает разрывы внешними данными, а свои числа показывает отдельным блоком с
  честным пустым состоянием.
- **Зависимость от сбора страниц.** Смена разметки источника ломает срез; смягчение — дата и пометка в клиенте
  (C5) и оповещение по возрасту.
- **Патчи клиента.** Чтение коллекции и драфта из памяти ломается при смене полей; чтение безопасное, с
  последней сохранённой копией.
- **Согласованность трёх репозиториев.** Маршруты A1 и A2 желательны, но не обязательны: у C3 и C4 есть путь
